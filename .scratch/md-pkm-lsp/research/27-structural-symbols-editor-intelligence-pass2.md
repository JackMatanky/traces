## 0. Premise corrections & new cross-ticket facts (load-bearing for the grilling session)

1. **VS Code's built-in markdown is itself a full LSP server and the biggest coexistence problem: pass 1 underweighted it.** `vscode-markdown-languageserver` runs over IPC and registers documentSymbol, workspaceSymbol, foldingRange, selectionRange, documentLink(+resolve), documentHighlight, codeAction, definition/refs/hover/rename, diagnostics; it has **no per-feature kill switch** (`markdown.server.enabled` does not exist; only whole-extension disable or per-kind `outline.show*` filters), and VS Code merges all providers per feature (`LanguageFeatureRegistry.ordered()`), so Traces **duplicates** symbols/folding/links/highlights by default. Feeds 15/23/32; grill-queue item #1 (B1 §F1.8, B7 §7, B3 §4.1).
2. **rumdl registers zero documentLink** (capability block verified at source: ends `..Default::default()`, digest gap, the local rumdl digest lacks `src/lsp/server.rs`; enumerate `FILE:` markers before trusting rumdl digest absences). rumdl also has zero folding/selection/codeLens/semanticTokens/documentHighlight; doubling with rumdl is only documentSymbol + workspaceSymbol (gated `enableSymbols`), codeAction is kind-disjoint (B7 §4, B3 §0).
3. **Marksman serves zero documentLinks**; pass-1's "implemented but unadvertised" reading was wrong: the digest hits are the vendored Ionide framework's `notImplemented` defaults (B3 §2.3). Same class of correction: Marksman's folding/selection "handlers" are also unreachable framework dead code (pass-1 found this; B2 reconfirms, capability block advertises neither).
4. **The wikilink-syntax-highlighting premise is refuted at source**: VS Code's built-in markdown TextMate grammar, nvim-treesitter, neovim core, helix, and Zed grammar queries all have **zero** wikilink rules; MDeiml's inline grammar has a `wiki_link` node behind build flag `EXTENSION_WIKI_LINK`, off in Zed/Helix builds. Semantic tokens would be the **only first-party coloring channel for wikilinks** in VS Code/Neovim; this strengthens the "in" case beyond pass 1's framing (B6 §1).
5. **`workspaceSymbol/resolve` pays for exactly one of four clients** (VS Code only); Neovim/Zed/Helix require full Locations; no Markdown peer resolves; r-a is eager. Proposed **amendment to ticket 23 §6** (uri-only+resolve+fallback → eager full Location, don't advertise resolve), input to 29 (B1 §F1.7, B7 §1).
6. **Zed has no evidence of `selectionRange` support** (two searches; pass 1 stated this as fact, B2 downgrades to "unverified, re-check"); Zed otherwise: documentSymbol/folding/codeLens/semanticTokens all **default off**, `lsp_document_links` default **on**, documentHighlight default on (75 ms debounce).
7. **Neovim `gx` documentLink support is 0.12+ only, calls resolve NEVER, and ignores target-less links**; Helix documentLink is master-only (merged 2026-03-14, not in any release ≤25.07.1). Eager targets are therefore a hard floor, not an optimization (B3 §4).
8. **Neovim sets `dynamicRegistration = false` for seven of our eight features** (all but codeAction) → static initialize-time capabilities + config gates are the only reliable channel; every peer Markdown server is static-first (B7 §2).
9. **A2 found a non-compiling API reference in ticket 11's answer**: it names `rope.line_to_utf16_cu(...)`; ropey 1.6.1 has no such method; the idiom is `rope.char_to_utf16_cu(rope.byte_to_char(offset))`. Decision intent stands; wording needs correction (A2 §4). Also reconfirmed: no `byte_to_utf16_cu` exists anywhere (pass 1 §0.3 already flagged the map's baseline claim; the ticket-level citation is the new find).
10. **A1 code-vs-design mismatches**: (a) Traces ships **minijinja 3.0.1** while ticket 22 designs `machinery::parse` behind an exact-pin `=2.24.0`, genuine mismatch to reconcile before implementation; (b) every seam 27 consumes (nav spine, overlay/ContentResolver, single-file RefreshPlan, spans, `src/template/analysis.rs`) is design-only/unimplemented, noyalib's YAML swap is the only partially-landed prerequisite; (c) `unique_tags()`/`unique_file_classes()`/`suggest_class()` (21's prereqs) do not exist yet; (d) headings are collected in a **second parse pass** (`collect_headings`), and GFM is not enabled (17's callout detection needs it).
11. **Marksman nests tags in its document outline** (children of headings), the only PKM peer precedent, directly contradicting ticket 16's "document symbols omit tags" pin; record to 16, don't decide here (B1 §F1.2).
12. **`documentSymbol` has no `partialResult`**; truncation is the only cap mechanism for it (B1 §F1.6).
13. **tower-lsp-server 0.23.0 (settled, paired with ls-types 0.0.6) has NO `Client` refresh methods**; `code_lens_refresh`/`semantic_tokens_refresh`/`folding_range_refresh` exist only in 0.24-rc. Any refresh design (CodeLens, semantic tokens) must either hand-roll the notification or wait on 0.24 (A2 §1.3, B7 §2).
14. **zk advertises `documentLink/resolve` but has no resolve handler** (phantom resolve); iwe advertises `inline_value_provider` returning `vec![]`. Both are the named advertise-without-implement anti-patterns for 29 (B3 §2.2, B4 §2.3).

### XII.1 The D3 inversion: 11 and 26 are NOT prerequisites for 27's document-scope features

The single largest change. Codegraph evidence: `parse_markdown` already receives full `ByteSpan`s from `into_offset_iter()` and discards the ends (parser.rs:111 vs :264-268); the shared walk (an LSP-side free function `walk(src) -> DocStructure`, cached per `(uri, version)` beside 14's BufferState) therefore produces **exact byte spans from day one** for blocks, inline events, and links. Consequences:

- **Wave 0** (prerequisites, no feature code): `[lsp]` config table + digest; `LineIndex` three-method extension (`line_start`, `byte_to_utf16_cu`, `utf16_cu_to_byte`) + 26's `convert` module wrapper; the ONE core-code visibility change: the already-budgeted (34:24) `LinkResolver` facade method `resolve_link(from, raw) -> Option<PathBuf>` (basename wikilinks cannot use `InlinkMap::has_target`; inlinks.rs:162 vs links.rs:268).
- **Wave 1** (ships BEFORE 11, 14-overlay, and 26 land): the walk; documentSymbol (headings + tasks); folding E-lite; selection S1; documentLink for wikilinks/embeds/standard links with exact spans; documentHighlight (a filter over walk link spans, no 26 spine dependency); CodeLens Option C (count = binary-search `entries` + `FileEntry::inlinks().len()`, entry.rs:168; zero-suppression free); semantic tokens two-valued (`unresolved` modifier only, classified via `resolve_link` Some/None).
- **Wave 2** (named-ticket-gated): three-valued resolution (Ambiguous token modifier, ambiguous-link tooltips) waits on 26's tie-reporting candidates; template-ref documentLinks/goto-def wait on 22's machinery spans (the ONLY genuinely span-gated link class); heading-level CodeLens counts wait on 26/38 heading-anchor edges (or interim per-doc scan); overlay-fresh counts/tokens wait on 14's RefreshPlan.

The walk is NOT a Note method and NOT merged into `collect_headings` (already a second parse, parser.rs:118; merging would put transient LSP spans into the postcard-persisted Note, which 11 §8 forbids). Folding runs on the raw walk, never the Note AST (fences/frontmatter/list-ends/callouts leave no AST residue). documentHighlight and selection do not need 11's spans (pass 2's "purest 11-dependence" claim was wrong). Task outline children use a single pass over `note.lists()` with ancestor stack per 23:43 (never `Note::tasks()` + depth; mis-nesting fixture `lists.rs:649`), still never QueryService (`QueryMode` is pub(crate), builder.rs:21, a 34 crate-split hazard) (earlier wording here said `Note::tasks()` with depth/parent; corrected 2026-10-22 to 23's pin after consistency review).

### XII.2 Answers to the three held grilling questions

**Q1 (outline convention, from D4)**: headings-only IS the universal convention: all five Markdown/PKM servers with documentSymbol (Marksman, markdown-oxide, MS languageservice, rumdl, iwe) emit headings only; zk emits none; no PKM LSP puts tasks in outline. BUT the stated reasons do not exclude tasks (mjbvz on vscode#201669: "standard markdown does not include task lists" = extension territory; artempyanykh on marksman#445: "a symbol is a definition, a link is a use"), the convention is **unexamined for tasks rather than rejected**, and a task IS a definition with stable identity. Closest non-heading precedents: MS link definitions (opt-in, `Constant`), Marksman nested tags (`String`), esbonio directives (reST). Decision: **tasks-in-outline is Traces-original and stays**; kind `Array` is additionally separable via VS Code's `outline.showArrays`, unlike headings (`String`) which collide with the built-in. Record the Traces-original status in the ticket.

**Q5 (unresolved drop, strengthened by D1 F3)**: drop stands. New pin: state the three-way handoff explicitly (25's diagnostic default severity; 15's create-note quickfix rides the diagnostic lane; 26's informational unresolved hover is the residual) AND the silent-hole consequence: severity `off` + drop = no link, no diagnostic, no action, hover only. That is a defensible user choice, but must be documented, not silent.

**Q11 (VS Code duplication, from D4)**: ecosystem-endorsed lever set, ranked: (1) accept duplicates as default (markdown-oxide practice: install and say nothing; we document), (2) document `outline.show*` per-kind filters (all LANGUAGE_OVERRIDABLE, verified in VS Code source) honestly, including the caveat that two `String` sources cannot be split by kind filters, (3) Traces-side per-feature config gates shaped like rumdl's `enableSymbols` for any proven-duplicative capability, (4) companion guidance: rumdl `enableSymbols = false` when Traces provides the outline, (5) whole-extension disable documented as the heavy option only. **Rejected**: SymbolKind dodge (zero precedent, breaks b1 kind pins); Marksman's VS Code identity-gating auto-cession (deletes Traces' task outline exactly where users see it).
