Supporting research for [ticket 26](../issues/26-definition-references-hover-rename.md), resolved by six parallel research subagents (R26-1 navigation substrate, R26-2 entity abstraction, R26-3 WorkspaceEdit mechanics, R26-4 position/encoding/Uri plumbing, R26-5 hover, R26-6 prepareRename/rename semantics), consolidated 2026-10-16. The general methodology rule (source/API demand vs ecosystem adoption as separate labeled judgments) was applied throughout.

## 0. Premise corrections & cross-ticket facts surfaced

These findings correct or sharpen assumptions in the ticket, the map, or settled tickets. Each is load-bearing for the grilling session and, where noted, for other tickets:

1. **The LSP type crate is `ls-types`, not `lsp-types`.** tower-lsp-server 0.23 re-exports `ls-types` (stale doc comment still says lsp-types), keyed on a fluent-uri `Uri` newtype (not `url::Url`), with built-in `to_file_path`/`from_file_path`. Both 26's framing and any code sketches must use `tower_lsp_server::ls_types`. **Pin the tower-lsp-server ↔ ls-types pairing**; ls-types forked the fixed Uri helpers back in, but a future lsp-types-0.97-style migration could drop them (re-verify at implementation time; feeds tickets 09/34).
2. **Ticket 11 cites a phantom ropey API.** `rope.line_to_utf16_cu` does not exist in ropey 1.6.1; the real idiom is `byte_to_char` + `char_to_utf16_cu` (two O(log N) hops). 
3. **Ticket 11 ↔ ticket 14 inconsistency on ropey.** Ticket 11's "two conversion functions (LineIndex for files / ropey for live buffers)" has nothing to split over: ticket 14 resolved `BufferState { content: String, version: i32 }`, no rope in the overlay. Disk and overlay both surface as `&str` via `ContentResolver::text_of`, so **one LineIndex-backed conversion helper serves both**. Reconcile 11↔14 in the ticket-26 writeup, not silently (R26-4).
4. **Hover latency is already budgeted.** Ticket 33's table 3 lists Hover <10ms target / <5ms stretch. No new budget needed.
5. **Ticket 11 left position-encoding negotiation undecided** (Question floated it, Answer didn't settle it). R26-4 supplies the decision: negotiate utf-8-if-offered-else-utf-16 (see Part IV).
6. **Local `docs/refs/lsp_spec.md` stubs key sections** (WorkspaceEdit, rename, hover, definition, references are `{% include_relative %}` bodies). Live spec fetches were mandatory; future tickets should not assume the local copy has these sections.
7. **`Schema`/`SchemaService` retain no source file path**, verified: `schemas_are_resolved_once_at_construction_not_reread_g_later` proves even the directory handle isn't kept. Goto-definition from a frontmatter field key to its schema TOML has no address today; ticket 26 must add origin provenance (one field) or accept convention-resolution.
8. **Frontmatter-embedded wikilinks are a reference blind spot**: they parse to `NoteFieldValue::Link` but never enter `outlinks`/LINKS. Obsidian's public `FrontmatterLinkCache` is key-scoped and **positionless**; no LSP peer supports frontmatter-link navigation at all. Traces' YAML-value span model (19) is ahead of the ecosystem, treat frontmatter links as first-class occurrences.
9. **Neovim never advertises `workspaceEdit.documentChanges`** (any version) yet its `apply_workspace_edit` applies `documentChanges` when present, and it never rolls back (per-doc soft skip on version mismatch). rust-analyzer exploits this; Marksman stays spec-faithful. Drives the Part III hybrid recommendation.
10. **VS Code advertises `positionEncodings: ['utf-16']` only and throws** if the server returns anything else. Zed is utf-16-only; Neovim 0.11+ and Helix advertise utf-8 first. Drives Part IV.
11. **Ticket 41 (spanned-occurrence persistence) evidence, corrected by Part VII.2**: the original claim here ("no PKM peer persists occurrence indexes; clangd is the sole persisted counterexample") is **false as of gopls v0.12 (Sept 2023)**, which persists per-identifier cross-reference indexes (go.dev/blog/gopls-scalability). The corrected picture: every major language server that stayed ephemeral (rust-analyzer) has 10-30s cold find-references at 1k-file scale (PR #16441); the two that persisted (clangd, gopls) are the responsive ones. Traces' in-memory-per-snapshot inverted index plus transient occurrence spans (option C) remains the recommended middle ground at 20K markdown notes, but the justification is now "markdown occurrence scanning is cheap (KB-scale notes, memchr-class throughput) and index maintenance is the measured failure mode elsewhere (markdown-oxide MAX_INDEXED_LINES, zk 7-minute cold index)", not "nobody else persists". 41-B (persisted occurrences) is the upgrade path if the re-parse-on-demand cost lands outside budget. See Part VII.2.
12. **markdown-oxide documents "(not zed)" next to all three of its rename features**, markdown-server ↔ Zed rename interoperability is a known failure zone. Test Traces' prepare/rename round-trip in Zed first (implementation-time check for 26/28).
13. **Traces codebase ground truth (codegraph review)**: no navigation/edit feature code exists at all today; `LineIndex` has only `new`+`line_at` (no UTF-16 conversion); `LinkResolver` is `pub(super)`; reference machinery exists only at note granularity (InlinkMap, `paths_with_tag`, `Tag::is_contained_in`); `unique_tags()`/`unique_file_classes()`/`suggest_class()` don't exist yet (ticket 21 prerequisites); no note-write path exists anywhere; refresh is whole-tree only; `unique_tags`-style occurrence queries have no backing; miette `QuerySyntaxError` is the only span-aware diagnostic precedent (miette 7.6 has **no** LspSpan, spans are byte offset+len; the miette↔LSP bridge is trivial and needs no adapter crate).

## Part I, Navigation data substrate (R26-1)

**How peers source find-refs/definition positions.** rust-analyzer: per-request cheap text prefilter (memchr) over in-memory file text in a SearchScope, then AST/name-resolve each hit (`ide-db/src/search.rs`); no persisted occurrence store, salsa is the index; and it is the measurably slow one (13.3s cold refs at 2,419 refs/257 files, PR #16441). gopls: historically a per-request snapshot walk, but **since v0.12 (Sept 2023) persists a cross-reference index** in its file-based cache (go.dev/blog/gopls-scalability; corrected by Part VII.2). clangd: `BackgroundIndex` with disk-cached `*.idx`, justified by C++ TU parse cost, and even it layers a live non-persisted `FileIndex` so actively-edited files never serve stale results. Markdown Oxide: eager whole-vault in-memory `Vault` (ropey + rayon), per-request reference selection. Marksman: in-memory suffix-tree + `docsBySlug`, per-document catalog rebuilt whole on edit. zk: SQLite note-granularity link graph (persisted) + per-request `strings.Index` line scan (occurrence positions computed on demand, first-occurrence-per-note only). MS markdown-ls: in-memory parse-all workspace cache, linear scan. **Verdict: a persisted occurrence store is the ecosystem exception; every PKM-class peer serves find-refs per-request over an in-memory index.**

**Three strategies for Traces** (spans transient per 11; <20ms find-refs budget per 33; overlay + 100ms T1 churn): (i) re-parse candidate files on request; (ii) occurrence-level inverted index rebuilt on refresh; (iii) note-granularity index (InlinkMap / PATHS_BY_TAG / paths_with_file_class) + occurrence re-scan of matching files only. Leanest = maximally capable here: **(iii)**, the rust-analyzer shape mapped onto Traces, inverted index gives O(1) candidate-file sets; per-candidate-file scan of already-parsed structural spans (or on-demand parse for closed files) confirms occurrences. Fits <20ms at 20K notes; memory cost ~zero (no new store); invalidation rides existing refresh. (ii) is the ticket-41 upgrade path if measured hot; (i) alone without the prefilter is the Dataview-shaped O(N) failure to avoid.

**Anchors/slugs.** VS Code markdown-ls: github-slugger regex, case-insensitive equality, parse-time dedupe (`slug-1`). Marksman: case-fold + strip punct + whitespace→`-`, GLFM heading-ID dedupe at parse (`-1` suffixes, on by default). rumdl MD051 validates standard-link anchors with multiple slug styles + auto-suffix awareness (in-tree precedent). Markdown Oxide: **exact heading-text matching only** (slugger exists but only feeds completion labels). zk: **strips anchors entirely**, goto lands at the note. Traces: GitHub-style slugger with parse-time dedupe (15's decided shape), living in one shared place so definition, 25's cross-file-anchor diagnostics, and rename all use it. rumdl's in-tree slugger is the reuse candidate to study.

**Ambiguity.** Spec demands nothing. Markdown Oxide returns all matches (matches ticket 15's "no diagnostic, return all candidates"); Marksman diagnoses ambiguity (per-type severity) AND returns multiple locations; hover takes first in both. Clients (Zed/Helix/stock-Neovim) jump to first, multiple Locations serve VS Code users (picker) but not the Neovim/Zed floor. 15's decision stands; hover should label when >1 rather than silently showing the first (markdown-oxide's silent-first is a known wart). `LocationLink.originSelectionRange` helps highlight the trigger but doesn't disambiguate.

**Location vs LocationLink.** Spec: references are `Location[]` only; definition may be `LocationLink[]` behind `textDocument.definition.linkSupport`. LocationLink carries targetRange/targetSelectionRange (required, zk omits them, non-conformant) + originSelectionRange. Peers overwhelmingly return plain `Location` (only zk emits LocationLink). Lean: `Location` everywhere v1, well-chosen ranges (heading title; `0:0-0:1` or first-line for files; key span for schema defs); LocationLink later if origin-highlight styling is wanted.

**Non-body definition targets.** Markdown Oxide: file targets get range `0:0-0:1`; file rename is a `ResourceOp::Rename` not a text edit. Schema-field goto needs the origin-provenance fix (§0.7). Reference-style link definition sites (15 D7) and footnote definitions (17) follow the same locate→target shape. Heading definition = its occurrence (title range).

**Reference semantics per entity.** Ticket 16 must confront markdown-oxide's deliberate-or-not split (goto-def exact-match, refs/rename hierarchical). Frontmatter-value links must enter the occurrence set (§0.8). `includeDeclaration` honored per MS's isDefinition/isTriggerLocation flag pattern. Hierarchical descendant inclusion for tags at occurrence granularity via `Tag::is_contained_in`.

## Part II, Entity abstraction & handler architecture (R26-2)

**Convergent mainstream pattern: three layers, two value types, no behavioral mega-trait.** (1) classify-the-occurrence-at-position; (2) a resolved target value; (3) per-feature rendering/serialization. rust-analyzer: `Definition<'db>` enum (classify step) → `NavigationTarget { file_id, full_range, focus_range, name, kind, container_name, … }` with the documented invariant **focus_range ⊆ full_range**; find-refs uses a *separate* `FileReference` occurrence type; rename returns protocol-free `SourceChange`; the outermost crate alone touches LSP types. typescript-go/tsserver: shared `createDefinitionLocations(originSelectionRange, clientSupportsLink, declarations, …)` building LocationLinks with **TargetSelectionRange ⊂ TargetRange**; `lsconv` is the dedicated protocol-conversion package. clangd: `Symbol` (definition-side) and `Ref`+`SymbolRole` (occurrence-side) are separate types; SymbolLocation "just covers the symbol name". gopls: **no navigation-target type at all**, sharing lives at the Mapper (offset↔line/col) + `[]protocol.Location` level. **The name-range vs full/container-range invariant is the convergent, load-bearing invariant across all of them.**

**PKM precedents.** Marksman: two-type model, `Element` (H/WL/ML/MR/MLD/T occurrence) with `linkAtPos`/`declAtPos` range-containment lookup; `Dest = Doc | Heading | LinkDef | Tag` (~one screen of pure helpers; Heading carries both `range` and `scope`, discovered independently the same focus/full invariant). Markdown Oxide: same two-type shape, worse hygiene, `Referenceable` with `Unresolved*` variants leaking into shared types, cross-product match arms with `_ => None` tax at every feature site; the cautionary tale (and project-health caveat limits its structural weight). zk: no def/refs/rename at all (completion+diagnostics only). **"Resolvable entity" is a real boundary, but of two small types and one resolve step, not a trait covering all operations.**

**Recommended shape for Traces, one thin protocol-free spine, two enums, no behavior trait:**

```
core (protocol-free; module home pending ticket 34, same status as 25's fold)
  nav::Occurrence        { kind: OccurrenceKind, span: ByteSpan, payload }
  nav::OccurrenceKind    Wikilink, Embed, RefLabel, Heading, Tag, Footnote,
                         FieldKey, InlineField, SchemaField, DailyDate
  nav::NavTarget         { kind: TargetKind, doc: PathBuf, name_range: ByteSpan,
                         scope_range: Option<ByteSpan> }   // Marksman Dest ∩ r-a focus/full
  nav::TargetKind        Note, Heading, Tag, Footnote, Field, SchemaField
  nav::locate(doc, pos) -> Option<Occurrence>          // one classifier, 24's ContextKind pattern
  nav::resolve(occ, ctx) -> Option<NavTarget>          // None is first-class (tags 16, dates 18)
  nav::references(target, ctx) -> Vec<Ref>             // shared driver + per-kind matcher
  nav::rename(target, new_name) -> Result<EditSet, RenameError>  // shared driver + per-kind rewrite
per-kind logic stays in domain modules that already own the semantics
  (Link::target_parts, Tag::is_contained_in, FieldKey, SchemaService,
   17's footnote index, 18's date matcher, GitHub slugger)
edge (LSP handlers only)
  LineIndex UTF-16 conversion, Location/WorkspaceEdit serialization, capability gating
```

Enum dispatch, not a `ResolvableEntity` trait: the entity set is closed today; a trait forces stub operations for None-kinds (tags have no definition per 16, dates per 18) recreating Markdown Oxide's noise as `Err(Unsupported)` arms; Traces' own precedent (24 ContextKind, 25 protocol-free fold) is enum + plain functions; exhaustive matches flag new entities at compile time. **OccurrenceKind ≠ TargetKind**, the two-sided split is the single most load-bearing peer lesson; folding them into one enum is the leaky shape to avoid. Not N independent implementations either: the spine (locate dispatch, NavTarget construction, refs driver, rename driver, edit/Location/UTF-16 plumbing) is small *because* it excludes everything that diverges; duplicating it nine times duplicates exactly the subtle bugs (range conversion, overlap checks, pre-validation ordering).

**Boundary placement.** The nav spine lives in core, consumes Index/Query/Schema/LinkResolver/ContentResolver, returns `ByteSpan`/`PathBuf`-based values, and **must not import ls-types**, same rule as 25's fold and 24's classifier; directly callable from the future MCP server (36) for free.

**Handler shape under concurrency_level(1).** Eager full-result construction inside the call (no streaming/lazy escapes, no progress); locate is O(document) via ContentResolver (no cached parsed_note); references/rename use index-first candidate selection, never full-vault scans; rename edits computed from occurrence spans, not by re-parsing 40 files. Copy peers' *data* discipline (preflight, range invariants, protocol-free edits), not their scheduling machinery (salsa cancel-by-panic, errgroup, inapplicable at N=1). Adopt a result-size ceiling with explicit truncation (gopls "presumed too numerous" analogue; clangd's max-file-count error).

## Part III, WorkspaceEdit construction & rename execution (R26-3)

**Client capability reality** (verified at source):

| Client   | documentChanges | resourceOperations | failureHandling     | changeAnnotations | notes                                             |
| -------- | --------------- | ------------------- | ------------------- | ----------------- | ------------------------------------------------- |
| VS Code  | true            | create/rename/delete | textOnlyTransactional | groupsOnLabel   | also metadataSupport, snippetEditSupport          |
| Zed      | true            | create/rename/delete | (default)           | none              | prepareSupport + DefaultBehavior:Identifier       |
| Helix    | true            | create/rename/delete | abort               | none              | normalizesLineEndings: false                      |
| Neovim   | **not advertised** | create/rename/delete |,                 | master only       | but `util.lua` *applies* documentChanges anyway   |

**Version policy.** `OptionalVersionedTextDocumentIdentifier.version: Option<i32>`; `None` = "disk is master" for non-open files (spec-sanctioned). Failure modes when wrong: VS Code rejects the **entire** edit set (version non-null and ≠ current, open docs only); Helix whole-edit fail; Zed binary-searches its last-10 versioned snapshots (`version == 0` treated as None, the gopls quirk: gopls sends literal `0` for on-disk files); Neovim checks the **first edit only** and soft-skips mismatched docs (**partial rename, no rollback**). Ecosystem-proven safe policy (rust-analyzer, Marksman): `Some(current_version)` for open/overlay docs, `null` for closed files. Never `version: 0`. Note the R26-6 tension: `version: null` disables VS Code's staleness protection (`validateWorkspaceEdit`), so null-for-closed is safe but null-for-open forgoes a free guard, use real versions for open docs.

Client-quirk datapoint (amended 2026-10-21 by iwe/fileclass research): iwe detects Helix from `client_name` and ships a Helix-specific 1-char-range code-action workaround — evidence that Helix's request shapes need per-client handling in production servers ([tool-iwe](tool-iwe.md) Part 6).

**Construction pattern.** Compute once as `Vec<(Uri, Vec<TextEdit>)>` (per-doc ascending-sorted, overlap-checked, ascending sort + overlap throw is vscode-languageserver-textdocument's canonical apply; same-start zero-width inserts keep array order); serialize via a ~10-line Marksman-style capability gate: `documentChanges` if the client advertised it, else `changes` map. Resource ops (CreateFile/RenameFile, seam to ticket 28 and 15's create-note action) gated on `resourceOperations` alone (rust-analyzer's resolution of the Neovim contradiction: ops work there despite documentChanges being unadvertised). Skip change annotations v1 (only VS Code + Neovim-master honor them; `needsConfirmation` for huge renames is v1 over-engineering). `metadata.isRefactoring` is worth setting on multi-file cascades to get VS Code's preview/confirm UI (Neovim users get no rollback, the preview is their only safety).

**No mature edit-application crate exists**, the ecosystem pattern is a hand-rolled ~50-100-line descending-sort-apply with overlap rejection (server side usually just sorts+validates; the client applies). `lsp-textdocument` is document bookkeeping only and uses lsp-types' Uri (integration seam). Traces: small in-house helper + tests that apply edits to a scratch buffer and assert post-apply text (gopls' fake-client applies edits into its test workspace, the strongest convention).

**Atomicity/failure.** **No mainstream client rolls back** (VS Code voids everything; Helix aborts mid-way; Neovim partially applies; Zed whole-transaction Result, but its server-initiated `applyEdit` handler answers `{applied: true}` even on deserialization failure, never trust that ack). Therefore atomicity is a **server obligation**: full pre-validation before responding (gopls `rename_check`, rust-analyzer `rename_error` → InvalidParams, MS `RenameNotSupportedAtLocationError`, clangd refuses unproven edits / stale index). Markdown Oxide (no validation, renames anything referenceable) is the anti-pattern.

**Performance & cancellation.** With concurrency_level(1), a running rename blocks all subsequent requests and cannot be cancelled. No mainstream server refuses oversized renames (clangd has a max-file-count error; that's the closest precedent). **Corrected by Part VII.1/VII.2: ticket 33's Answer table 3 does list Rename (<100ms p95 / <30ms stretch, "may use `$/progress` for large workspaces")**, so the budgets below are restated as scaling *expectations under 33's binding row*, not new prices: prepareRename <5ms (it's a locate); rename scaling tiers should be **byte/occurrence-count based, not file-count based** (tsserver 6s on vscode, snacks.nvim 0.5s client-side apply for 300 edits/190 files; markdown notes are KB-scale so precomputed-span renames are cheaper than code LSPs). The 12-vs-33 disagreement on `$/progress` (12 defers it, 33 allows it for large workspaces) and the N=1 stall risk (a 1s rename makes every subsequent hover wait 1s, violating hover's own budget; tower-lsp docs and markdown-oxide PR #473 are the cautionary evidence) are surfaced as grilling decisions, see Part VII.4.

**Post-rename refresh.** No server mutates its index optimistically pre-save (no precedent). Marksman relies on the client's didClose(old)+didOpen(new) dance (lean, protocol-fragile); rust-analyzer drives one `apply_change` path from notifications; Markdown Oxide's full-rebuild-on-watch is the documented anti-pattern. Traces: client applies edits → didChange (open files, overlay) + watched-file events (closed files, ticket 10) → T1 100ms coalesced refresh; staleness window ≤100ms, same as typing. A 40-file rename yields 40 events, ticket 13's single-file RefreshPlan constructor needs a **batch/multi-file constructor** (seam to 13, not bolted onto 26).

**Write-path seam.** No markdown LSP writes note content server-side for rename; edits flow through the response; file renames are client-side `RenameFile` ops. Seams: 26 owns occurrence-text edits; **28 owns `RenameFile` + cascading link-text updates** (ops execute in document order: edits to old path precede the rename, edits to new path follow); 15's create-note code action = `CreateFile` (+ optional initial-content edit, version null, rust-analyzer precedent).

**Uri interop.** `Uri` serde is strict (malformed client URI fails the whole message, acceptable, surface via 12's error path). `to_file_path` does **no scheme check**; `from_file_path`'s "returns None if file doesn't exist" doc is misleading (only relative paths canonicalize). Policy: gate `scheme == "file"` at every boundary; always emit absolute file URIs; echo client-spelled URIs verbatim in responses (never round-trip a client-named doc through from_file_path, Windows canonical form ≠ editor string match); `HashMap<Uri,…>` keys by exact received string; cross-reference the vault by decoded path, never string surgery; no canonicalization machinery v1 (gopls-style `ParseDocumentURI` normalization is the documented upgrade); skip+log non-file schemes (untitled:) in rename. Clippy `mutable_key_type` papercut on Uri keys → `#[allow]`/config.

## Part IV, Position encodings, conversion, Uri keying (R26-4)

**Negotiation reality.** Spec: utf-16 is the only mandatory encoding; client sends ordered `general.positionEncodings`; server echoes its pick via `capabilities.positionEncoding`; "conversion is best done where the file is read." Clients: **VS Code `[utf-16]` only, throws on anything else**; **Zed `[utf-16]` only**; **Neovim 0.11+ `['utf-8','utf-16','utf-32']` utf-8 first**; **Helix `[utf-8, utf-32, utf-16]` utf-8 first**. Servers: rust-analyzer/Biome negotiate and deliberately skip utf-16 (deviation Traces needn't copy); ty prefers utf-8; gopls never sets positionEncoding (always UTF-16 by omission); clangd natively both.

**Recommendation: negotiate utf-8-if-offered-else-utf-16.** Pick the first encoding in the client's preference order that Traces implements; never offer utf-32; default utf-16. Cost ~20 lines (`negotiate()` + one match arm + one ServerCapabilities field). Payoff: for Neovim 0.11+ and Helix (half the first-class targets), `character` = line-relative byte offset, conversion is zero work and zero unicode surface; VS Code's throw can never fire; Zed unaffected. This closes ticket 11's open negotiation question.

**Shared conversion-helper shape** (Biome/ty/croma-lsp style; **it also is the miette bridge**, miette SourceSpan is byte offset+len, no adapter crate exists or is needed):

```
convert (protocol boundary module)
  PositionEncoding { Utf8, Utf16 }
  negotiate(&ClientCapabilities) -> PositionEncoding      // stored on Session, echoed at init
  to_lsp_position(&LineIndex, BytePos, PositionEncoding) -> Position
  to_lsp_range(&LineIndex, Range<ByteSpan>, PositionEncoding) -> Range
  to_byte_pos(&LineIndex, Position, PositionEncoding) -> BytePos   // inbound, the direction 11 never covered
```

All functions **total** (clamp, never panic, croma-lsp's gate: malformed mid-edit offsets must still yield in-bounds ranges). Inbound clamp semantics = VS Code `offsetAt`: line past EOF → doc end; char past line end → before terminator (CRLF: exclude `\r`); surrogate halves round **down**. Outbound: whole-document pure-ASCII fast path (gopls) + naive O(line-prefix) UTF-16 walk for v1, ~50-100µs worst case on the pathological 51KB line, within 24's S6 0.5ms/range budget; rust-analyzer's `line-index` 0.1.2 crate (per-line non-ASCII tables) is the measured-if-hot upgrade. Astral chars and combining marks are correct for free via `char::len_utf16()` (code units, not graphemes, exactly what the protocol wants). Strip leading U+FEFF once at ContentResolver (VS Code strips BOM on decode; a disk-reading server otherwise sees a 3-byte shift). Tabs: positions count code units; nothing to do. Encoding is an explicit parameter threaded from the session, never a global (the tsgo horror story).

**One helper serves every consumer**: definition/references/hover/rename responses, diagnostics (25), completion TextEdits (24), folding/symbols (27), and miette `SourceSpan` inputs (u32 `TryFrom` narrowing per 11).

**Uri keying pitfalls** (for 14's `HashMap<Uri, BufferState>` and WorkspaceEdit maps): percent-encoding case variants (`%20` vs `%20` hex case; colon `file:///C:/` vs `file:///C%3A/`, ls-types synthesizes the encoded-colon form on Windows); drive-letter case; symlinks stay distinct keys (editor-spelled URIs are document identity everywhere, never canonicalize through symlinks); multi-root folder↔document matching by decoded path (ticket 30 seam). Per-spelling keys + path-based cross-referencing is the v1 answer; gopls' full normalization is the upgrade if two-spelling duplication ever bites.

## Part V, Hover architecture, kind, content parity (R26-5)

**Kind negotiation.** All four verified clients send Markdown in `hover.contentFormat` (Zed and Helix are **markdown-only**; VS Code `[Markdown, PlainText]` + `general.markdown` parser info; Neovim `[Markdown, PlainText]`). Server precedent: rust-analyzer/clangd, Markdown iff contentFormat contains Markdown, **absent ⇒ PlainText** (clangd default-PlainText; gopls formats the body per kind, the kind-dependent-conversion precedent). Recommendation: same semantics; **PlainText = stripped rendering of the same composed body** (one composer, two formatters, never raw markdown in a plaintext field; Helix's rust-analyzer comment documents that failure mode). PlainText is the long-tail path, tested once, not the design center.

**Rendering reality / safe subset.** Helix: pulldown-cmark + strikethrough only; renders headings, lists, syntax-highlighted fenced code, bold/italic/strike, inline code; **HTML as literal text; links lose the URL; images unhandled**. Neovim: markdown scratch buffer + treesitter (full). Zed: full markdown incl. tables and clickable links; client cap `MAX_HOVER_BYTES = 100_000` with fence repair. VS Code: markdown-it + sanitizer; `isTrusted`/`supportHtml`/`supportThemeIcons` all default **false** and settable only client-side. **Intersection-safe subset: bold/italic/strikethrough, inline code, fenced code, lists, links (text-only loss in Helix), `---` rules. Banned: raw HTML, images, tables, `command:` links, theme icons, and headings** (ticket 19's settled rationale; Markdown Oxide's `` `# Backlinks` `` H1 is the counterexample to ignore, it's VS Code-only). One escaping helper in the renderer (MS `escapeMarkdownSyntaxTokens` convention: backslash `\ `` * _ { } [ ] ( ) # + - ! ~ `` ``, inline-code backtick-padding by longest-backtick+1).

**Architecture, one locate step, one shared renderer, per-entity producers.** Peers share the *locate* step between hover and other features (rumdl shares `resolve_link_path` with completion/definition; MS reuses `MdLinkProvider.getLinks`; Marksman reuses `linkAtPos`) but never rendering. Traces-internal: 24's per-(uri,version) content snapshot + ContextKind dispatcher feed locate; 22 Q11 explicitly scoped hover *content* out of 26's entity abstraction. Shape:

```
locate(uri, pos) -> Option<EntityAt>            // shared with def/refs (nav::locate, Part II)
producer(kind)   -> HoverBody { badge, body_md, body_plain }   // per-entity, ticket-owned
renderer         -> MarkupContent { kind: negotiated, range: Some(span) }
```

Latency: 33's existing hover row (<10ms/<5ms); in-memory snapshot lookup only, never a reparse; overlay reads via ContentResolver only for preview strings. **Always set `range` to the token span** when ticket-11 spans exist (rust-analyzer/typescript/MS camp); `None` only where spans don't exist.

**Per-entity parity matrix** (Traces decision → peer comparison; "-" = no peer support):

| Entity                        | Peer precedent                                                                                              |

## Part VI, prepareRename & per-entity rename semantics (R26-6)

**prepareRename conventions.** Spec: `Range | {range, placeholder} | {defaultBehavior} | null`; clients are **not required** to call prepare; "RenameOptions may only be specified if the client states prepareSupport", **Marksman's capability-gated advertisement is spec-mandated, not cargo-cult** (advertise `RenameOptions{prepare_provider:true}` iff client announced prepareSupport, else plain `true`; handlers registered unconditionally). All four target clients announce prepareSupport (Zed adds DefaultBehavior:Identifier); VS Code falls back to word-at-cursor when prepareProvider is absent. Per-server: rust-analyzer bare `Range`, errors → InvalidParams; gopls `{Range, Text=name}` and **capability-gates file-rename in prepare** ("client does not support file renaming", user learns before typing); tsserver `{TriggerSpan, DisplayName}`, failures → **RequestFailed (-32803)**; clangd placeholder = decl name, refuses on stale index; MS markdown-ls per-kind RangeWithPlaceholder (fragment links get the **target's header text** as placeholder; display-text positions **reject**); markdown-oxide **has no prepareRename at all** (anti-pattern).

### VII.3 Design-alternative audit (codegraph-grounded)

Grounding facts (codegraph, verified): `ByteSpan` exists at src/position.rs:79 with start<=end invariant; `Spanned<T>` at src/position.rs:359 is value-ord and single-typed (not a fit for occurrences); **no navigation/edit feature code exists anywhere**; the parser sees spans (`handle_event(ctx, event, span)`, src/note/parser.rs:241) but **discards them**, and `Link`/`Heading`/`Tag` carry no position fields, so occurrences must be computed from text per request (independently confirming transient-spans); `LinkResolver` is pub(super) and resolves note paths only (no anchors/headings/tags); reference machinery is note-granularity (InlinkMap, paths_with_tag); no position→element lookup exists anywhere; 24's ContextKind and 25's fold are settled designs, not code; the codebase idiom is enums + service facades + plain functions (QueryService, SchemaService, IndexerService), no behavioral mega-trait anywhere.

Alternatives considered vs the spine: (a) no spine, methods on existing types: rejected, `Link` has no span so locate is structurally impossible without the new type anyway, and the subtle shared code (range conversion, overlap checks, pre-validation ordering) duplicates 4-9x; (b) single Entity enum collapsing the occurrence/target split: rejected, it deletes the load-bearing peer invariant and recreates markdown-oxide's cross-product tax; (c) merge into src/index/: rejected, inverts dependency direction (index would transitively know schema/footnotes/dates) and violates 34's leaf-module constraint; (d) trait ResolvableEntity: rejected, forced stub arms for legitimate None-kinds, loses exhaustive-match flagging; (e) **hybrid refinement of the proposal: adopted**.

VII.3 amendments adopted into Q1:

1. **Payload folded into the kind**: `Occurrence { kind: OccurrenceKind, span: ByteSpan }` where variants carry domain payloads (`Wikilink(Link)`, `Embed(Link)`, `FrontmatterLink(Link)`, `Heading(Heading)`, `Tag(Tag)`, `FieldKey(FieldKey)`, ...). The loose payload field was the only element making wrong-payload states representable.
2. **Context struct facade**: operations hang off a small `NavContext` (borrowed bundle of index/schema/config/content-resolver handles) following the QueryService/SchemaService/IndexerService facade idiom, so ticket 36's "N protocol adapters" and the LSP handlers call one obvious API.
3. **Two named changes to existing code, budgeted not discovered**: expose `LinkResolver` via a `resolve_link`-style facade method (or widen from pub(super)); expose `paths_with_tag` via the same facade.
4. **locate vs 24's ContextKind are NOT shared code**: both walk a document from a position, but completion's contract (region/replace-range/filter-word, pre-edit) and nav's contract (spanned occurrence, post-parse) diverge exactly where unifying would hurt. Record so no future refactor "helpfully" merges them.
